## Local contract used to assess fit

These were local contracts, not upstream requirements. Current versions: [README.md](../../README.md), [SYNC.md](../../.claude/skills/SYNC.md), [Main](../../.claude/skills/sdd-main/SKILL.md), and the [Planner](../../.claude/agents/sdd-planner.md), [Implementer](../../.claude/agents/sdd-implementer.md), [Reviewer](../../.claude/agents/sdd-reviewer.md) profiles.

- Main alone talks to the user and coordinates fresh isolated sessions; subagents cannot spawn subagents.
- Planner owns specs, tickets and ADRs. Main owns discovery, brief, `docs/CONTEXT.md` and orchestration state. Main does not write code.
- Implementer works one ticket or an explicit Batch, and on correction fixes sibling occurrences of a cited defect class within the function/module.
- Reviewer stays read-only, reviews exactly immutable `base_sha..head_sha`, verifies criteria and evidence, and avoids speculative out-of-scope refactors.
- Canonical domain vocabulary and current decisions remain in `docs/CONTEXT.md`; ADRs remain in `docs/adrs/`. Existing [discovery](../../.claude/skills/sdd-grill-with-docs/SKILL.md) and [implementation](../../.claude/skills/sdd-implement/SKILL.md) overrides already preserve these paths and ownership.

## Ranked conditional recommendations

These are proposed adaptations, not descriptions of what the repo already does.

### 1. Use diagnosis discipline for hard failures

**Trigger:** an intermittent bug, performance regression, failed criterion, or correction whose root cause is not yet demonstrated. **Owner:** Implementer within its ticket/Batch; Main handles unavailable access and user decisions. **Quality gained:** proof of the symptom before patching, a smaller repro, measured hypothesis tests and original-scenario verification. [Upstream diagnosis](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/diagnosing-bugs/SKILL.md).

**Minimal adaptation:** add a conditional invocation in `sdd-implement` with SDD glossary/ADR paths. Record the executed failing command and result, cause, fix and passing command in existing handoff evidence. Its Phase 3 hypothesis message is a nonblocking user checkpoint, not an approval gate; an isolated Implementer records hypotheses rather than contacting the user. Missing environment or a material design gap returns through existing `blocked_technical`/`blocked_design`. A missing regression-test seam does not authorise architecture work outside the ticket. Keep the existing sibling-correction rule: diagnosis complements it.

### 2. Make seam reasoning explicit during planning

**Trigger:** an uncertain public interface, new seam, or difficulty testing the required behaviour through existing interfaces. **Owner:** Planner; Reviewer may use the vocabulary to explain a concrete defect or cost. **Quality gained:** smaller caller contracts and better test placement before implementation. [Core design reference](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/codebase-design/SKILL.md).

**Minimal adaptation:** conditionally consult the core reference while writing testing/implementation decisions. Prefer existing interfaces and real variation; record chosen seams in the spec/ticket. Core vocabulary is useful without another agent or mandatory abstraction. Do not invoke the [parallel alternative-design procedure](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/codebase-design/DESIGN-IT-TWICE.md) from Planner/Reviewer. Product-cost changes still become `questions_pending`; ADRs remain Planner-owned. TDD [already reaches this reference](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/tdd/SKILL.md) when Implementer interface shape is uncertain, so an extra Implementer hook would duplicate coverage. Reviewer findings still require location, impact and evidence, not a preference for deeper modules.

### 3. Resolve external factual uncertainty before freezing the brief

**Trigger:** documentation, compatibility or service behaviour is an unsettled prerequisite to a product decision. **Owner:** Main delegates a narrowly scoped research task. **Quality gained:** cited, reusable facts rather than guesses or repeated document reads. [Research contract](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/research/SKILL.md).

**Minimal adaptation:** Main owns dispatch and the research output path; give the researcher the job directly rather than asking it to invoke the skill and spawn again. Research is an optional support task outside the three delivery roles, never a substitute for an unavailable Planner/Reviewer. Return one cited note and pass only its reference into discovery/Planner. If adding a support role is undesirable, keep research as a separate task before SDD. Do not add another authoritative state or make research mandatory for local, already-settled facts.

### 4. Review repeated workflow friction after the run

**Trigger:** repeated correction classes, a failed handoff, or an unusually costly session; preferably an explicit retrospective request. **Owner:** Main/maintainer after completion or escalation. **Quality gained:** evidence-based improvements to navigation, verification and reviewer standards. [Retro procedure](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/retro/SKILL.md).

**Minimal adaptation:** leave user-invoked rather than adding a new phase. Use session logs, persisted reviews and Git as primary evidence; propose the smallest change. Mechanical mistakes favour an existing deterministic check over another prose rule. Prior local testing had identified sibling-overflow and handoff failures, whose fixes were already present at review time. Validate fast-path and escalation behavior before expanding orchestration.

### 5. Use a prototype only when conversation cannot settle behaviour

**Trigger:** a concrete state-model or UI question that must be seen or exercised before spec synthesis. **Owner:** Main coordinates user feedback; a separately scoped spike owns code. **Quality gained:** discover incorrect assumptions before freezing requirements. [Prototype](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/prototype/SKILL.md), [logic shape](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/prototype/LOGIC.md), [UI shape](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/prototype/UI.md).

**Required adaptation:** this is not a drop-in Main skill: it writes code, captures a branch and promotes decisions, while Main cannot write code and Implementer needs an approved ticket. Safest current option is a separate pre-SDD prototype task, then feed its verdict/reference into discovery. An integrated spike would require an explicit role-contract extension, separate branch/worktree ownership and a clean return boundary. Planner captures the validated decision; prototype code is not silently shipped. Keep this below the cheaper diagnosis/design pointers.

### 6. Keep maintenance and completion tools at their own boundaries

**Trigger:** editing this harness or preparing a requested PR. **Owner:** maintainer uses [writing-for-agents](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/productivity/writing-for-agents/SKILL.md); Main uses [pr](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/pr/SKILL.md) when writing a PR body. **Quality gained:** precise conditional pointers and completion criteria; concise evidence and understandable change impact.

**Minimal adaptation:** prefer one pointer per demonstrated need and disclose branch-specific details. Respect this repo's canonical/generated agent split and sync process. Use `docs/CONTEXT.md` for PR vocabulary; PR preparation must not alter ticket approval or add an unsolicited publishing step. These tools were available in the review environment and needed no new implementation phase.

## Why not adopt the upstream orchestrator

Upstream [ask-matt](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/ask-matt/SKILL.md) recommends preserving discovery through tickets in one context. SDD intentionally separates those phases with committed explicit briefs. Upstream [implement-spec](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/implement-spec/SKILL.md) adds parallel worktrees and merger agents and reviews the whole integration branch at the end. Those are alternative workflow semantics, not missing SDD features. Likewise, upstream [code-review](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/code-review/SKILL.md) uses `HEAD` and two spawned review agents. Retain exact-range independent review and Batch approval here.

Ordinary cold resume must continue to trust committed `PROJECT_STATE.md` and Git. Upstream [handoff](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/productivity/handoff/SKILL.md) is useful for portability, but its prose cannot become competing state. Whole-codebase architecture surveys, decision maps, TypeScript-specific tooling, and git safety hooks earn separate scoped work only when needed; none belongs in every ticket's path.

## Evidence limits and next step

This is a source/contract review, not a runtime benchmark. Expected quality gains are recommendations, not measured reductions in bugs, tokens or correction rounds. No skill catalogue guarantees improved behaviour by itself. Start with one conditional diagnosis pointer and Planner design coverage, then exercise a hard bug and a seam-ambiguous feature through the existing handoffs. Assess actual evidence and correction rounds before adopting the more expensive research/prototype support paths.
